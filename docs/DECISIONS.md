# 설계 결정 기록 (DECISIONS)

각 항목: 무엇을 / 왜 / 실서비스에서는 어떻게.

## D-01 VC 증명 형식: JWS(EdDSA) 봉투형 (vc+jwt), Data Integrity 대신
- 무엇: VC/VP 를 JWT compact JWS 로 서명한다 (`typ: vc+jwt`, `vp+jwt`). 페이로드는 W3C VC 2.0 데이터 모델 JSON.
- 왜: 정규화(JCS/RDF) 버그 위험이 없고 TS/Python 모두 표준 라이브러리로 검증 가능. 6일 일정에서 구현 위험이 가장 낮다.
- 실서비스: `eddsa-jcs-2022` Data Integrity 또는 SD-JWT VC 로 전환 가능. 검증 절차(§9)는 형식과 독립적으로 유지.

## D-02 발급기관 DID 메서드: `did:dbp:<id>` (레지스트리 조회형)
- 무엇: 발급기관 DID Document 는 `IssuerRegistry` 컨트랙트에서 생성한다. 홀더는 `did:key`.
- 왜: did:web 은 호스팅 도메인이, did:ethr 은 추가 컨트랙트가 필요. 시연 범위에서는 원장 레지스트리가 곧 DID 문서다.
- 실서비스: resolver 인터페이스만 교체해 did:web / did:ethr 로 전환.

## D-03 규칙 엔진: JSON Logic 부분집합 자체 구현, 정수 연산만
- 무엇: `var, if, and, or, !, ==, !=, <, <=, >, >=, in, *, +` 만 지원. 불리언 전용 논리, float 금지. 퍼센트 비교는 `소득×100 <= 기준×퍼센트`.
- 왜: 외부 json-logic 라이브러리는 언어별 의미가 미묘하게 다르다(truthiness, 숫자 변환). TS/Py 동일 출력과 동일 번들 해시가 핵심 요구.
- 실서비스: 그대로 사용 가능. 규칙 변경 시 version 상향 + 원장 등록.

## D-04 발급기관별 '아는 필드' 분리, 부분 프로필 허용
- 무엇: 대구시는 주민등록·가구·소득·수급 정보만, iM뱅크는 신용구간·연소득만 안다. 전처리는 없는 입력을 None 으로 두고, 발급기관은 자기 소관 claim 만 평가한다.
- 왜: "지자체·은행은 서로 개인정보를 직접 공유할 수 없다"는 제안의 전제를 코드 구조로 강제하기 위해.
- (2026-10-09 주) iM뱅크 발급기관은 D-15 에서 제거되었다. 현재 연소득 사실은 사회보장정보원(복지기관)이 발급한다.

## D-05 상태 목록 인덱스는 무작위 배정
- 무엇: Bitstring Status List 인덱스를 0~131071 중 미사용 무작위 값으로 배정.
- 왜: 순차 배정은 발급 순서·규모를 노출한다. 무작위 배정 + 덩어리 공개로 특정 시민 역추적을 어렵게 한다.

## D-06 원본 프로필의 '소득인정액'을 월 소득으로 단순화
- 무엇: 생계·주거·교육급여, 기초연금의 소득인정액(소득평가액+재산의 소득환산액)을 `monthlyIncomeKRW` 하나로 대체. 부양의무자 기준 제외. 기초연금은 1인 가구=단독, 2인 이상=부부 기준.
- 왜: 소득환산 계산은 MVP 범위 밖. 정책 JSON `notes` 와 화면 각주에 명시한다.
- 실서비스: 발급기관(대구시) 내부 판정에 공식 산식을 적용하고 claim 정의는 그대로 유지.
- (2026-10-09 주) 통신요금 감면에 새로 넣은 기초연금 경로(65세 이상 AND 기초연금 선정기준액 이하)도 이 단순화를 따른다. 기준 중위소득은 1~6인 고시값만 쓰고 7인 이상 가구는 6인 값으로 판정한다(MVP 한계, D-22).

## D-07 로컬 체인 기본값은 Hardhat, Besu QBFT 는 compose 프로필
- 무엇: 개발·테스트·기본 시연은 Hardhat 노드(chainId 31337). Besu QBFT 4노드 compose 는 `chain/besu/` 에 제공.
- 왜: 개발·테스트 반복 속도(Hardhat 즉시 채굴). Besu QBFT 는 2026-09-14 실제 기동해 배포·발급·검증·폐기·PII 스캔까지 검증했다 (`chain/besu/README.md`). 컨트랙트·클라이언트는 `RPC_URL` 만 바꾸면 동일하게 동작한다.
- 실서비스: Besu QBFT 권한형 네트워크에 대구시·은행·복지기관이 validator 로 참여.

## D-08 AI 는 규칙 엔진 결과 안에서만 고른다
- 무엇: `/recommend` 후보는 규칙 엔진이 적격으로 판정한 정책뿐. LLM 출력은 인용 검증기를 통과해야 노출되고, 실패 시 템플릿 설명으로 대체.
- 왜: 불변 조건 1·7. AI 오류가 잘못된 자격 안내로 이어지지 않게 한다.

## D-09 홀더 본인 확인은 챌린지 서명 + 모사 로그인(citizenId)
- 무엇: 발급 요청 시 홀더가 발급기관 챌린지에 did:key 로 서명한다. 실명 인증은 시민 식별자 선택으로 모사.
- 실서비스: 모바일 신분증 인증으로 교체. 챌린지 서명(키 보유 증명)은 그대로 유지.

## D-10 지갑: 동의 화면은 발급기관별로 순차 표시, ✔ 목록은 그 기관이 발급 가능한 모든 사실
- 무엇: 대구광역시(7개 사실) → iM뱅크(2개 사실) 순으로 동의 화면 2개. 거짓인 사실은 VC 로 만들지 않고 "발급 불가" 로 표시한다.
- 왜: "true 인 사실만 발급" 원칙(불변 조건 2). 기관마다 동의 범위를 따로 명시해야 최소 수집 원칙에 맞는다.
- (2026-10-09 주) 현재 순서는 대구광역시 → 사회보장정보원(D-15)이고, 김복례(C-001)는 4 + 7 = 11개 사실을 발급받는다(D-21).

## D-11 지갑: 규칙 번들·정책 문서를 IndexedDB 에 캐시
- 무엇: 발급기관이 꺼져 있어도 사전 판정·추천 화면이 뜬다. 캐시되는 것은 공개 규칙 텍스트뿐이다.
- 왜: 시연 중 네트워크 문제로 화면이 비는 일을 막기 위해.

## D-12 검증기관: 같은 요청에 대한 두 번째 제출·공격 시연 결과는 별도 키로 저장
- 무엇: 원래 요청의 PASS 결과는 유지되고, 재사용·만료 공격은 `requestId#attack-…` 키로 기록된다.
- 왜: 공격 시연 뒤에도 결과 화면이 그대로 남아야 발표 흐름이 끊기지 않는다.

## D-13 개발용 앱 포트: 3000 이 사용 중이면 지갑을 3010 으로
- 무엇: `scripts/demo.sh` 가 포트 점유를 감지해 지갑 3000→3010, 검증기관 3001→3011 로 옮긴다. 이 머신은 3000 을 다른 프로젝트가 쓰고 있었다.

- 무엇: Python 3.12.10 은 hidden 플래그가 붙은 `.pth` 를 건너뛰어 editable 설치가 깨진다. `scripts/fix_venv.sh` 가 `chflags -R nohidden .venv` 를 실행하며 `make setup`·데모 스크립트가 호출한다.

## D-15 (아이디어 개정, 2026-09-14) 은행은 발급기관이 아니라 검증기관이다
- 무엇: 발급기관을 공공(대구광역시 + 사회보장정보원 모사)으로 한정하고, iM뱅크 발급기관을 제거했다. 신용평점 하위 20% 여부는 `issuerOf: "self"` 로 두어 VC 로 발급하지 않고 지갑 사전 판정에만 쓴다. 연소득 3,500만·4,500만 원 이하 사실은 복지기관이 발급한다(소득금액증명 원본 대체).
- 왜: 개정된 제안의 핵심은 "공공이 판정한 자격을 민간 금융기관 창구에서 원본 없이 확인"이다. 은행이 스스로 발급한 사실을 스스로 검증하면 블록체인의 필요성(서로 다른 신뢰 도메인)이 사라진다. 신용평점은 은행이 신용정보사에서 직접 조회하는 정보라 시민이 증명할 대상이 아니다.
- 실서비스: 복지기관 발급기관은 사회보장정보시스템(행복e음) 연계로, 연소득 사실은 국세청·건강보험 소득자료 연계로 교체.
- (2026-10-09 주) 새희망홀씨 현행 기준에 맞춰 연소득 4,000만·5,000만 원 이하 사실도 복지기관이 발급한다(D-21).
- (2026-10-09 주) 신용평점은 여전히 VC 로 만들지 않지만, 창구가 먼저 조회한 값은 프리셋의 `counterChecked` 로 정책 판정 재현에 들어간다(신용 하위 20% 고객용 프리셋 2종, D-22).

## D-16 (아이디어 개정) 정책을 '복지멤버십 안내 대상'과 '은행·민간 창구 혜택'으로 구분
- 무엇: 정책마다 `channel`(welfare·transport / finance·discount)과 `welfareMembership` 를 두고, 지갑·AI 는 finance·discount(햇살론뱅크·새희망홀씨·소액생계비대출·통신/전기/도시가스 감면)를 먼저 자세히, 공공 복지는 "복지멤버십에서 안내"로 짧게 다룬다. 정책은 9 → 13개, 판정 270 → 390건.
- 왜: 복지멤버십이 이미 163종을 안내하므로 안내 기능을 다시 만들지 않는다는 개정 제안의 입장을 화면 구조로 드러내기 위해.
- (2026-10-09 주) 햇살론뱅크는 2026.1.2 개편에 맞춰 햇살론 일반보증으로 바꿨다(D-21). 정책 수 13개·판정 390건은 그대로.

## D-17 (아이디어 개정) 검증기관은 은행·저축은행 창구, 용도 프리셋으로 요청 항목 최소화
- 무엇: 행정복지센터 검증기관을 제거하고 iM뱅크 지점·iM저축은행(모사)만 둔다. `GET /presets` 가 서민금융 상담(2항목)·햇살론뱅크·새희망홀씨(연소득 1항목)·감면(1항목) 프리셋을 제공하고, 검증 결과에 `policyCheck`(제출된 항목만으로 정책 규칙 재현)를 넣는다.
- 왜: 공공기관 사이의 확인은 행정정보 공동이용이 이미 담당한다. 창구마다 "무엇을 받으면 되는가"를 프리셋으로 고정해야 과잉 요청을 막을 수 있다.
- (2026-10-09 주) 현재 프리셋은 서민금융 상담(2항목)·햇살론 일반보증(연소득 3,500만 원 1항목)·새희망홀씨(연소득 4,000만 원 1항목, 은행 창구만)·감면(1항목)이고, 프리셋마다 취급 창구 종류(`verifierKinds`)를 둔다(D-21).
- (2026-10-09 주) 프리셋은 6종이다(신용 하위 20% 고객용 햇살론 일반보증·새희망홀씨 추가). `policyCheck` 는 제출되지 않은 항목을 더 이상 거짓으로 채우지 않는다: 제출 항목 + 창구 확인값(`counterChecked`)만으로 결과가 정해지지 않으면 `eligible: null` 과 결과를 가르는 항목(`pending`)을 돌려준다(D-22).

## D-18 (2차 개정, 2026-09-14) 제품 축을 "종이 없애기"에서 "조회형(pull) → 보유형(hold)"으로
- 무엇: 공공 마이데이터(전자정부법 제43조의2, 이용기관 154곳)가 소득금액증명을 금융회사에 직접 제공하므로 "은행에서 종이 증명서를 없앤다"는 주장을 폐기했다. 대신 조회형의 한계(원문 값 전달·반복 조회·이용 내역 3년 보관·대면 창구 부재)와 보유형의 3성질(참·거짓만 / 1회 발급 N회 제출 / 검증이 이력을 남기지 않음)을 제품의 전부로 정의했다. 공공 마이데이터는 경쟁자가 아니라 2단계 입력(`IssuerDataSource`)이다.
- 왜: 선행사례 조사에서 종이 논리가 반박당했다. 3성질은 단일 기관 DB·직접 조회 방식으로 재현할 수 없으므로 블록체인 필요성의 본체가 된다.
- 문서·화면 규칙: "유출 불가", "개인정보가 사라진다", "종이를 없앤다", "행정기관 사이에서만 작동" 문구 금지(검증기관 앱 테스트가 src/ 전체를 검사).

## D-19 비교 패널의 숫자는 하드코딩하지 않고 data/comparison.json 에서 온다
- 무엇: `data/legacy-documents.json`(소득금액증명·주민등록표 등본·수급자증명서의 서식 항목과 출처, claim→서류 매핑) → `scripts/pii_items.py` 가 프리셋별 조회형 항목 수·보유형 항목 수·감소율을 계산하고 예시 VP 로 보유형 항목 수를 실측해 `data/comparison.json` 을 만든다. 검증 서비스는 같은 함수(`dbp_verifier.comparison.build_comparison`)로 검증 결과마다 `comparison` 블록을 붙이고, 앱은 그 값만 표시한다.
- 왜: 프리셋이 늘어도 화면이 자동으로 따라오고, "실제 API 호출 결과가 아니라 서식 기준 비교"라는 정직성 표기를 데이터에 같이 담기 위해.
- 결과: 햇살론뱅크·새희망홀씨 10→1 (90%), 서민금융 상담 13→2 (85%), 공공요금 감면 13→1 (92%). 종전 "10개 항목 기준 80%" 지표는 이 계산으로 대체했다.
- (2026-10-09 주) 프리셋 키가 `sunshine-bank` → `sunshine-general`(햇살론 일반보증)로 바뀌었고, 새희망홀씨는 연소득 4,000만 원 1항목을 받는다. 두 프리셋 모두 소득금액증명 10항목 → 1 (90%)로 숫자는 그대로다(D-21).

## D-20 (2026-09-14) compose 네트워크 격리는 프로브가 잡아낸 결함을 고친 뒤에야 성립했다

- 왜: 심사위원이 고시표·한전 약관과 대조하면 바로 반증되는 데이터 오류였고(어르신 페르소나를 고르면 전기요금 '적격'인데 요구 증명서는 발급받을 수 없고, 실제 대상인 통신요금은 '부적격'으로 숨겨졌다), OR 분기로 적격이 된 시민(예: 신용 하위 20%이면서 연소득 4,500만 원 이하)은 지갑에서 '적격'인데 창구에 낼 증명서가 없었다. 단일 분기만 적은 `requiredClaims` 와 미제출 항목을 거짓으로 채우는 `policyCheck` 는 규칙식과 증명 경로가 따로 노는 구조적 원인이었다. 혜택패스가 증명하는 것은 소득·자격 사실뿐이고, 신용평점·재직·보증 심사용 소득 증빙은 여전히 창구가 확인한다.
- 실서비스: 지속 원장에 한 번이라도 등록된 버전은 D-03 대로 버전을 올려 새로 등록한다(이번 예외는 등록 이력이 없는 버전에만 해당). 기준 중위소득·기초연금 선정기준액 같은 연도별 고시값은 고시표 원문 값을 하드코딩한 대조 테스트로 고정하고, 7인 이상 가구는 고시 산정식을 전처리에 넣는다. 정책 문서의 증명 조합은 규칙식에서 자동 도출해 둘이 어긋나지 않게 검사한다.
