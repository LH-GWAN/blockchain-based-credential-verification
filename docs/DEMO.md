# 시연 스크립트 (①~⑦, 약 8분)

준비: `make setup` 1회 → `make demo` → 지갑 http://localhost:3000 (모바일 폭으로), 검증기관 http://localhost:3001 (데스크톱). 3000 이 사용 중이면 스크립트가 지갑을 3010 으로 띄우고 주소를 출력한다.
리허설 없이 전체 흐름을 확인하려면 `make e2e` (Playwright 가 ①~⑥ 과 ③′ 을 15초 안에 재현하고 `docs/screenshots/` 를 갱신한다). ⑦은 `E2E_ISSUER_DOWN_CMD="pkill -f dbp_issuer" make e2e` 로 함께 재현할 수 있다(끝나면 아래 "⑦ 뒤 발급기관 재기동"으로 다시 띄운다).
발표 노트북 한 대로 진행할 때는 브라우저 창 두 개를 좌우로 배치한다. QR 대신 6자리 코드 입력이 가능하다.
**순서 주의**: ⑤ 폐기는 ⑦ 발급기관 정지보다 **먼저** 한다(E2E 순서와 같음). ⑦에서 발급기관을 끄면 ⑤의 `:8003` 폐기 요청이 연결 거부로 실패한다.

> 페르소나: 대구 북구 거주 68세 1인 가구 "김복례"(가명·합성 데이터), 월 소득 100만 원, 연소득 1,200만 원, 신용평점 하위 20%(창구 자체 조회). 발급받는 사실 11개(대구광역시 4 + 사회보장정보원 7).
> 시연 상품은 2026년 현행 기준이다: **햇살론 일반보증**(2026.1.2 개편 — 근로자햇살론·햇살론뱅크 통합, 은행·저축은행 모두 취급), **새희망홀씨**(연소득 4,000만 원 이하 또는 신용평점 하위 20%이면서 5,000만 원 이하, 은행권 전용). 혜택패스가 증명하는 것은 소득 요건뿐이고, 재직·사업 3개월 이상과 소득 증빙 요건·신용평점은 창구가 자체 확인한다(규칙 번들 `daegu-eligibility@2026.2` 에 넣지 않음).
> 한 줄: **공공이 판정한 자격을 시민이 보유하고, 은행 창구에 참·거짓만 제출한다.** (조회형 → 보유형)
> 보여줄 3성질: ① 값이 아니라 참·거짓 ② 1회 발급 → N개 창구 ③ 발급기관도 중계자도 제출 이력을 모른다(검증 때 발급기관에 조회가 가지 않는다. 원장에는 검증기관 주소·시각이 붙은 제출 영수증 솔트 해시 1건만 남고, 누구의 무슨 제출인지는 없다). "종이 증명서를 없앤다"는 말은 쓰지 않는다.

### ⑦ 뒤 발급기관 재기동 (저장소 루트에서)

가장 간단한 방법은 다른 터미널에서 `make demo-issuers` 다(= `./scripts/demo.sh issuers`, `make demo` 와 같은 포트·`.demo/issuer-*.db`, Ctrl+C 로 종료). 직접 띄우려면 아래처럼 한다.

`make demo` 가 띄운 것과 같은 DB 파일을 지정해야 한다. `ISSUER_DB_PATH` 를 빠뜨리면 `./issuer-welfare.db` 를 새로 만들어 이전에 발급한 증명서가 `CREDENTIAL_UNKNOWN`(404)이 된다.

```bash
RULE_EVAL_DATE=2026-09-14 ISSUER_ID=daegu   ISSUER_PORT=8001 ISSUER_DB_PATH=.demo/issuer-daegu.db   uv run python -m dbp_issuer > .demo/issuer-daegu.log 2>&1 &
RULE_EVAL_DATE=2026-09-14 ISSUER_ID=welfare ISSUER_PORT=8003 ISSUER_DB_PATH=.demo/issuer-welfare.db uv run python -m dbp_issuer > .demo/issuer-welfare.log 2>&1 &
curl -sf localhost:8001/health && curl -sf localhost:8003/health   # 둘 다 응답하면 완료
```

이렇게 다시 띄운 발급기관은 `make demo` 의 자식 프로세스가 아니므로, 시연을 끝낼 때 `pkill -f dbp_issuer` 로 함께 정리한다. 재기동하면 발급기관은 원장에 아직 게시하지 못한 폐기(⑤에서 503 이 났던 경우)를 원장 상태목록과 합쳐 다시 게시한다. compose 로 띄웠다면 `docker compose start issuer-daegu issuer-welfare`.

## 예상 질의 → 화면으로 답하기
- **공공 마이데이터로 이미 되지 않나?** → ⑥ 비교 패널: 공공 마이데이터가 해결한 것은 서류 조달이다. 전달되는 것은 여전히 원문 항목 전체이고, 기관마다 다시 조회되며, 이용 내역이 3년 보관된다. 혜택패스는 공공 마이데이터를 대체하지 않고 2단계 입력으로 쓴다(원문은 발급기관에서 멈춘다).
- **서민금융 잇다가 하고 있지 않나?** → ⑦ + ③′: 잇다는 비대면 조회·추천 플랫폼이고 조회형이다. 상담이 창구로 넘어가면 자격 확인은 다시 원문 문제가 된다. 혜택패스는 시민이 보유한 참·거짓을 어느 창구에나 반복 제출하고, 검증은 발급기관을 거치지 않는다.
- **복지멤버십이 이미 하고 있지 않나?** → ② 화면: 공공 복지는 "복지멤버십 안내 대상"으로만 표시하고, 혜택패스는 그 다음 단계(창구 증명)와 복지멤버십에 없는 은행·민간 혜택을 맡는다.
- **민간인증서·전자증명서로 다 되지 않나?** → ③ 요청 확인 화면: 인증서는 "본인"을 확인하지만 "연소득 3,500만 원 이하"라는 사실은 증명하지 못한다. 혜택패스는 그 사실을 공공 발급기관 서명으로 전달한다.
- **남는 기록이 정말 없나? 결과 화면에 원장 트랜잭션이 보이는데?** → ⑥ 패널 우열 그대로 답한다: "없음"이 아니라 **원장에 제출 영수증의 솔트 해시 1건**이 남는다. 그 트랜잭션에는 앵커한 검증기관 주소와 시각이 공개되지만 제출 내용·시민 식별 정보는 없고, 솔트는 영수증을 만든 창구와 시민 지갑만 알아 원장만 보는 제3자는 해시로 내용을 추정할 수 없다. 발급기관에는 조회 자체가 가지 않아 조회 기록이 생기지 않는다. 창구는 자기 검증 결과를 보관한다(받은 쪽의 기록). 한계: 시민 수가 적을 때는 발급 직후의 앵커 시각으로 제출을 추정할 여지가 있어, 실서비스에서는 일괄 앵커·앵커 주소 분리를 검토한다(D-23).
- **창구 앞에 있는 사람의 증명서인지 어떻게 아나?** → ③·④의 확인 숫자 4자리: 지갑과 창구 화면이 같은 VP 에서 같은 숫자를 계산하므로, 직원이 방문자의 휴대폰 화면과 맞춰 본다. 다만 이것은 "이 휴대폰에서 낸 제출"까지만 묶는다. 방문자가 코드를 원격의 다른 사람에게 넘겨 대신 제출하게 하는 경우는 숫자 대조로만 완화되고, 신원 결합은 로드맵(모바일 신분증 VP 를 함께 제출)이다(D-23).
- **증명서 ID 와 지갑 DID 는 식별자 아닌가?** → 맞다. VP 에는 참·거짓 1개와 함께 증명서 메타데이터(발급기관, 지갑 DID, 증명서 ID `jti`, 상태목록 인덱스, 유효기간, 규칙 번들·버전)가 넘어가고, 같은 증명서를 두 창구에 내면 두 창구가 같은 DID·ID 로 기록을 이을 수 있다. ⑥의 "1개"는 사실 항목 수다. 창구 간 연결을 끊는 것은 로드맵(창구별 pairwise DID, BBS+ 선택적 공개)이다(D-23).
- **"390건 100% 일치"의 기준은?** → 공식 기관 판정과 대조한 정확도가 아니라 **판정 일관성**이다: 규칙 엔진(TS·Python)이 같은 팀이 정책식을 따로 옮긴 참조 구현(`packages/rules/py/src/dbp_rules/reference.py`)의 기댓값(`expected.json`)과 390건 모두 같다. 해석 오류는 두 구현에 함께 들어갈 수 있어(F04·F05 가 그랬다), 기준 중위소득 고시값은 원문 대조 테스트로 따로 고정했다(D-22). 공식 판정 대비 정확도는 측정하지 않았다.
- **검증 0.013초는 QR 부터 결과까지인가?** → 아니다. 검증 서버의 `/present` 처리 시간(로컬 Hardhat, 같은 증명서 2장, 50회)이고 QR 처리·VP 생성·지갑 통신은 빠져 있다. 측정 조건은 `docs/TEST_REPORT.md` 에 적고, 목표(2초)와 비교하는 값으로만 쓴다.
- **원장 개인정보 0건은 무엇을 검사했나?** → `chain/scripts/scan-pii.ts` 가 모든 블록의 calldata·이벤트 로그에서 합성 시민 30명의 이름·citizenId·생년월일·소득(문자열과 `uint256` 정수 인코딩), 주민번호 패턴, 소득/생년월일 필드명, JWT, 시민 지갑 DID 를 찾은 결과다. 해시·압축된 값이나 다른 정수 폭은 이 스캔이 아니라 **원장에 쓰는 경로가 해시·공개키·상태 비트뿐**이라는 구조(`packages/ledger-client`)로 답한다.
- **확인번호(6자리)만 알면 남의 결과를 볼 수 있나?** → 아니다. 6자리 코드로는 요청 내용만 볼 수 있고, 만료·사용된 코드는 404, 실패 조회가 잦으면 429 다. 결과 조회는 요청을 만든 창구 화면(창구 토큰) 또는 그 VP 를 낸 지갑(VP 해시)만 할 수 있다(D-23).
- **상품 기준이 바뀌면?** → 2026.1.2 햇살론 개편을 실제로 반영한 경로로 답한다: 규칙 번들을 `2026.1` → `2026.2` 로 버전을 올려 원장에 새로 등록했다(원장의 (번들, 버전) 항목은 불변, D-03·D-21). 증명서에는 판정에 쓴 번들·버전·해시가 들어 있어 검증기관이 원장과 대조하고, 창구는 받는 규칙 버전 목록(`ACCEPTED_BUNDLES`)을 정해 목록 밖 버전은 `RULE_VERSION_NOT_ACCEPTED` 로 거절한다. 증명서 유효기간은 발급일 + 1년과 기준 중위소득 고시 연도 말 중 이른 날이고, 틀린 규칙으로 발급한 증명서는 발급기관이 번들·버전 단위로 한 번에 폐기한다(D-23). 창구 프리셋은 상품을 취급하는 업권과 함께 관리한다(새희망홀씨 = 은행만).
- **김복례는 68세인데 햇살론 일반보증 재직 요건은?** → 재직·사업 3개월 이상과 소득 증빙은 신용평점처럼 창구가 자체 확인하는 요건이다. 혜택패스는 소득 요건(연소득 3,500만 원 이하) 한 가지를 원본 없이 증명하는 부분만 맡는다.
- **신용 하위 20% 고객은?** → 창구가 신용평점을 먼저 조회한 뒤 '· 신용 하위 20% 고객' 프리셋으로 연소득 4,500만 원 이하(햇살론 일반보증, 은행·저축은행) 또는 5,000만 원 이하(새희망홀씨, 은행만) **1항목**을 받는다. 신용평점은 증명서가 아니라 창구 확인값(`counterChecked`)으로 정책 판정 재현에 들어가고, 비교 패널은 똑같이 10 → 1 (90%)이다. 지갑의 창구 안내에도 이 경로가 함께 적혀 있다(정책마다 OR 분기별 증명 조합, D-22).
- **기초연금 받는 어르신의 통신요금·전기요금은?** → 이동통신요금 감면은 기초연금 수급 어르신도 대상이다(이용료 50%, 월 최대 11,000원 — 복지로 안내). 규칙은 이 경로를 '65세 이상 = 참' + '기초연금 선정기준액 이하 = 참' 두 증명서로 판정한다(기초연금 수급 자체가 아니라 선정기준 충족을 월 소득으로 근사한 판정 — D-06. 실제 감면은 통신사·복지로가 기초연금 수급 여부로 확인). 전기요금 복지할인은 한전 대상 목록에 기초연금 수급자가 없어 수급자·차상위만 판정한다. 예: 합성 시민 신정숙(C-013, 65세 1인 가구, 월 150만 원)은 통신요금 감면 대상, 전기요금 복지할인은 해당 없음. 시연용 '공공요금 감면' 프리셋은 차상위 경로('기준 중위소득 50% 이하') 1항목만 받으며, 비교 기준 서류는 소득금액증명·주민등록표 등본이다.
- **실제 기관이 발급하는가?** → 발급기관 `/.well-known/issuer` 와 `docs/DECISIONS.md` D-09: 모사 발급기관이며 모바일 신분증·마이데이터 어댑터로 교체되는 구조(`IssuerDataSource`).
- **키를 잃어버리면?** → 관리 화면 폐기 + 재발급. 자격의 원천은 지갑이 아니라 발급기관.
- **AI 가 틀리면?** → ②의 배지와 인용 검증. `services/ai` 테스트: 존재하지 않는 조항을 인용하거나, 부적격 제도를 언급하거나, 정책 문서에 없는 숫자를 쓴 추천 항목은 노출되지 않는다. 채팅 답변에는 "자격 판정이 아님" 안내가 붙고, 적격 여부는 규칙 엔진 결과만 따른다.
- **블록체인이 꼭 필요한가?** → ④ 네트워크 격리 + 원장 조회 체크리스트: 검증기관은 발급기관에 묻지 않고도 공개키·폐기 상태·규칙 버전을 확인한다. 발급기관에는 제출 시점·상대에 대한 조회가 가지 않는다(원장에는 검증기관 주소·시각이 붙은 솔트 해시만 남는다). 격리 근거는 `make compose-isolation-up && make demo-isolation` — 라이브 시연 스택이 아니라 **별도 compose 인스턴스**를 검사하며, 대조군(발급기관 응답)을 먼저 확인하므로 ⑦에서 발급기관을 정지하기 **전에** 실행한다(F50).

## 리허설 초기화
- 발급기관: `curl -X POST localhost:8001/admin/demo/reset` (복지기관은 8003). 관리 API 는 로컬에서만 열리며, `ADMIN_TOKEN` 을 설정했다면 `-H "X-Admin-Token: $ADMIN_TOKEN"` 을 붙인다. 지갑: 설정 → **지갑 초기화**.
- reset 은 발급기관 DB 만 비우고 **원장의 폐기 비트는 지우지 않는다**(폐기는 되돌리지 않는다). 원장까지 처음 상태로 돌리려면 `make demo` 를 끝내고(Ctrl+C, 직접 재기동한 발급기관은 `pkill -f dbp_issuer`) 다시 띄운다 — Hardhat 체인이 새로 시작된다.
- 규칙 번들 `2026.2`(해시 `0xb24ad5f2…d94e`, D-22)로 바뀐 뒤 처음 리허설할 때는 지갑을 초기화해 이전 버전(`2026.1`)이나 이전 2026.2 해시로 발급된 증명서와 캐시를 지운다(남겨 두면 `RULE_HASH_MISMATCH` 또는 `RULE_VERSION_NOT_ACCEPTED`).
